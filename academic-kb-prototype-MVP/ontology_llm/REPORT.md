# Онтология, созданная LLM, и сравнение с онтологией, созданной вручную

Основа: Lippolis et al., «Ontology Generation using Large Language Models» (arXiv 2503.05388, 2025).

## 1. Что сделано

1. Составлены **пользовательская история** и **20 компетентностных вопросов (CQ)** по предметной области (`ontology_llm/cq.json`): поиск публикаций по объекту и типу исследования, иерархия «провинция → область → район → месторождение → пласт → залежь», авторы и выходные данные, параметры месторождений, пластов и залежей.
2. Написан скрипт `scripts/generate_ontology_llm.py` с двумя методами из статьи: **Memoryless CQbyCQ** (на каждый CQ отдельный запрос без памяти, фрагменты объединяются) и **Ontogenia** (диалог с памятью, метакогнитивная подсказка, онтология дорабатывается по одному CQ). Использует тот же ключ, что и чат (DeepSeek).
3. Онтология сгенерирована методом **Memoryless CQbyCQ**: 20 независимых фрагментов (`ontology_llm/generated/claude_cqbycq/CQ*.ttl`) и объединённый файл `merged.ttl`.
4. Написан скрипт `scripts/compare_ontologies.py`, считающий метрики статьи; результаты в `ontology_llm/results/comparison.md`.

Сравниваются три онтологии:

| Обозначение | Что это |
|---|---|
| **manual_original** | ваша онтология `oil-gas-ontology.owl` (Protégé), только схема |
| **manual_v22** | ваша онтология + расширения приложения (цепочка свойств, обратное свойство, непересекающиеся классы, DOI, год открытия, координаты, ключ записи БД), уровень схемы |
| **claude_cqbycq** | онтология, сгенерированная LLM по методу CQbyCQ |

## 2. Важные оговорки (честно)

- **Генерировала Claude (Sonnet 5.5), а не DeepSeek.** В среде, где я работал, нет ключа DeepSeek. Memoryless CQbyCQ выполнен так: каждый фрагмент написан по одному CQ и пользовательской истории, без обращения к соседним фрагментам. Это воспроизведение протокола, а не вызов API. Для диплома нужно один раз запустить `generate_ontology_llm.py` на вашей машине с DeepSeek и сравнить; сравнивающий скрипт работает с любым файлом.
- **CQ написаны мной** по схеме БД и описанию руководителя, то есть они не независимы от того, что хранится в базе. Это занижает «лишнее» у онтологии, построенной по БД, и завышает долю смоделированных CQ у тех, кто моделировал БД подробно.
- **Соответствие «слот ↔ элемент онтологии» (какой элемент закрывает какое требование CQ) составлено вручную**, как решение эксперта; скрипт проверяет, что элемент существует и подходит по области определения, а вопросы про вывод (транзитивность, поднятие связи вверх) проверяются реально, выводом OWL 2 RL на тестовых данных.
- Ловушки OOPS! проверены **собственной реализацией 12 правил** (P04, P05, P06, P08, P10, P11, P13, P19, P29, P34, P35, P39), а не веб-сервисом OOPS!. Для диплома стоит дополнительно прогнать файлы через сайт OOPS!.
- Один прогон, статистической значимости нет.

## 4. Анализ

**Где LLM лучше.**
- Полнее покрывает данные: параметры месторождения (глубина, обводнённость, координаты), пласта (свита, толщина, тип коллектора, проницаемость, пористость), залежи (тип нефти, запасы) и организацию автора (CQ11, CQ16–CQ18). Ваша онтология и v22 моделируют только иерархию, публикации и типы исследований, а параметры, которые есть в БД, в онтологии отсутствуют. Это реальный пробел и для v22.
- У всех элементов есть метки (ru/en) и комментарии; в вашей онтологии их почти нет (ловушка P08, 28 элементов).
- Домены и диапазоны указаны у всех свойств (в вашей: у `имеетМесторождение`, `имеетПласт`, `имеетЗалежь` их нет, и они дублируют `входитВ`).

**Где LLM хуже** (типичные дефекты, описанные в статье, воспроизвелись):
- **Свойство `partOf` получило четыре области определения и четыре области значений** (P19), потому что каждый CQ по отдельности объявлял «своё» `partOf` (Field→District, Horizon→Field, Deposit→Horizon, …), а при объединении в OWL множественные области определения означают пересечение. Результат: после вывода каждый объект получает типы остальных классов (провинция становится «районом», «месторождением», «пластом»): 25 ложных типов на тестовой цепочке из шести объектов. Рассуждатель HermiT при этом не видит противоречия, потому что классы не объявлены непересекающимися. Это ровно то, что статья называет «неверные области определения и значений».
- Транзитивное свойство с разными областями определения и значений (P29).
- Класс `Oblast` остался несвязанным (P04): в одном фрагменте объявлен, в иерархию не включён.
- Дубликаты (`publicationYear` / `publishedInYear`): следствие отсутствия памяти между запросами.
- Нет заголовка `owl:Ontology` (P39), нет непересекающихся классов (P10).
- Нет знания предметной области: нет «зоны нефтегазонакопления», типы исследований — индивиды, а не классы.

**Где ваша онтология сильнее.**
- Единая иерархия: общий суперкласс `НефтегазовыйОбъект`, транзитивное `входитВ` с корректными областями (оба конца — `НефтегазовыйОбъект`), поэтому вывод не загрязняет типы.
- Типы исследований как подклассы класса `Исследование`, удобно для определяемых классов.
- В v22: цепочка свойств `относитсяКОбъекту ∘ входитВ ⊑ относитсяКОбъекту` (CQ2, CQ14, CQ20 работают; в исходном файле нет — 3 CQ частично), непересекающиеся классы, DOI, связь с БД и проверка на реальных данных (HermiT совпадает с OWL 2 RL на 1705/1705 выводах).

## 5. Вывод для руководителя

LLM по методу CQbyCQ быстро даёт **покрывающую** онтологию (100 % CQ, богатые атрибуты, аннотации), но не **согласованную** модель: каждый вопрос закрывается отдельным локальным решением, а при слиянии возникают множественные области определения, неверная транзитивность и дубликаты (то же наблюдают авторы статьи). Ручная онтология меньше по охвату (60 % CQ в исходном виде, 80 % в v22), зато логически чистая и позволяет выводить новое знание. Практический вариант: **гибрид** — взять каркас и аксиомы вашей онтологии и дополнить его атрибутами и аннотациями, предложенными LLM, а Ontogenia (с памятью) должна дать меньше дубликатов и конфликтов, чем CQbyCQ; это нужно проверить запуском на DeepSeek.

## 6. Как воспроизвести

```
python -m scripts.compare_ontologies                  # три онтологии, owlrl + HermiT (нужны rdflib, owlrl, owlready2, Java)
python -m scripts.generate_ontology_llm --method cqbycq    --out ontology_llm/generated/deepseek_cqbycq
python -m scripts.generate_ontology_llm --method ontogenia --out ontology_llm/generated/deepseek_ontogenia
```
Для файла от DeepSeek нужен `ontology_llm/mappings/<имя>.json` (по образцу `claude_cqbycq.json`: пространство имён `http://example.org/westsib#`, слоты и имена элементов), затем `--extra <имя>=<файл>`.
