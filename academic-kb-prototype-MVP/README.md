# Академическая база знаний — прототип (новая схема, Лаб. работа №9)

Backend + React-фронтенд академической базы знаний по исследованиям и
разработке нефтегазовых месторождений Западной Сибири, реализованные
по физической модели данных IDEF1X из Лабораторной работы №9
(`db/schema_lab9.sql`):

```
Province → Oblast → Rayon → Field → Horizon → Deposit
(провинция) (область) (район) (месторождение) (пласт) (залежь)
```

Публикации связаны с геологическими объектами через три ассоциативные
сущности: `publication_field`, `publication_horizon`, `publication_deposit`
(две последние добавлены сверх исходной лабораторной работы — в ней
была только `publication_field`). Авторы нормализованы в отдельную
таблицу `author` и связаны через `publication_author`.

> Это вторая версия схемы прототипа. Первая (универсальная таблица
> `objects` с `parent_id`) заменена на типизированную — каждый уровень
> иерархии теперь отдельная таблица с явным внешним ключом.

## Что реализовано

| Компонент | Статус |
|---|---|
| Реляционное хранение (province…deposit, publication, author) | ✅ SQLAlchemy ORM (`app/models.py`), соответствует `db/schema_lab9.sql` |
| Навигация по иерархии | ✅ `app/hierarchy.py` — обход FK (без OWL/rdflib, структура уже в самой схеме) |
| Агрегация публикаций по уровню | ✅ Публикация пласта/залежи корректно "поднимается" до района/области/провинции |
| RAG-поиск (TF-IDF + фильтры) | ✅ `app/search.py` |
| LLM-генерация ответа (DeepSeek/Groq/Gemini) | ✅ `app/llm.py`, с graceful fallback на шаблон |
| Загрузка документов (PDF/DOCX/TXT → чанки) | ✅ `app/document_processing.py`, привязка к `publication_id` |
| Внешний поиск публикаций (OpenAlex + Crossref) | ✅ `app/sources/`, с автоматическим разбором ФИО авторов в нормализованные записи |
| GIS (координаты есть только у `field`) | ✅ `GET /api/gis/fields`, PostGIS `GET /api/gis/fields/nearby` |
| React-фронтенд (карта, карточка, поиск, чат, внешний поиск) | ✅ `frontend/` |

Все пункты протестированы вживую на настоящем PostgreSQL 16 + PostGIS
в процессе разработки (не только на SQLite) — включая парсинг
координат `"широта,долгота"` в геометрию и агрегацию публикаций через
все три ассоциативные таблицы.

## Установка и запуск

### 1. База данных

```bash
# Если нужна только структура (например, для защиты лабораторной работы):
psql -U postgres -d <ваша_база> -f db/schema_lab9.sql
psql -U postgres -d <ваша_база> -f db/seed_example_lab9.sql   # пример данных, опционально

# Для запуска backend'а (создаёт те же таблицы через SQLAlchemy и
# сразу наполняет примером Шаимского района):
set DATABASE_URL=postgresql+psycopg://postgres:ваш_пароль@localhost:5432/ваша_база
python -m scripts.seed_db
```

> **Драйвер:** `postgresql+psycopg://` (psycopg3), не `postgresql+psycopg2://`
> — на Windows с не-английской локалью системы psycopg2 падает с
> `UnicodeDecodeError` при получении NOTICE-сообщений сервера не на
> английском. psycopg3 этой проблемы лишён.

По умолчанию (без `DATABASE_URL`) backend использует SQLite — для
быстрой разработки без установки PostgreSQL.

### 2. PostGIS (опционально, для `/api/gis/fields/nearby`)

```bash
python -m scripts.migrate_postgis
```

Добавляет geography-колонку `geom` к таблице `field`, разбирая строку
`coordinates` ("широта,долгота"). Требует установленного расширения
PostGIS на сервере (через Stack Builder на Windows).

### 3. Backend

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Swagger: http://localhost:8000/docs

### 4. Чат-бот с LLM (опционально)

Скопируйте `.env.example` в `.env`, впишите один из ключей:

| Провайдер | Платно? | Ключ |
|---|---|---|
| Groq (Llama 3.3 70B) | Бесплатно | https://console.groq.com/keys |

### Как чат-бот отвечает

**Сначала определяется вид сообщения** (`app/services/intent.py`):
- «Привет», «как дела», «спасибо», «пока» — ответ сразу, без поиска и без LLM;
- «что ты умеешь», «помощь» — описание возможностей по реальному состоянию базы (число публикаций, у скольких
  есть аннотация и полный текст, подключён ли LLM) и перечень ограничений;
- «Привет, расскажи про Шаимское месторождение» — это вопрос: приветствие отбрасывается, остальное идёт в поиск
  (сообщение считается разговорным, только если после вычёркивания приветствий и стандартных фраз в нём не
  осталось содержательных слов);
- если в базе ничего не нашлось, определяется, относится ли вопрос к теме вообще (LLM отвечает «тема» или «вне»;
  без LLM — проверка по терминам предметной области). Для вопросов вне темы («погода», «рецепт борща»)
  публикации не ищутся, ни локально, ни во внешних источниках, а бот объясняет, о чём база.
Без LLM проверка по терминам может отказать и по-настоящему тематическому вопросу, если в нём нет известных слов.
Тогда ответ мягче («не удалось связать вопрос с темой, переформулируйте»).

**Дальше** — как описано ниже.

На каждый вопрос (`POST /api/chat`) модель получает три вида контекста:

1. **Справка из базы знаний** — структурированные данные об объектах, которые названы в вопросе:
   иерархия «провинция → область → район → месторождение → пласт → залежь», заполненные
   параметры, число связанных публикаций. Пустые поля в справку не попадают, и модели
   запрещено их домысливать (`app/services/kb_context.py`).
2. **Локальная база публикаций.** Поиск идёт по *фрагментам* (аннотация, полный текст), а не по
   склеенной строке; публикация оценивается по лучшему фрагменту, а в модель уходят именно
   совпавшие фрагменты. Вопрос ищется на двух языках: исходный и английская формулировка от
   LLM; кроме того, `app/services/glossary.py` переводит предметные термины, поэтому русский
   вопрос находит англоязычные аннотации даже без LLM. Переводы ищутся отдельными запросами со
   своим весом, а не подмешиваются к вопросу: подмешивание размывало запрос и ухудшало выдачу на
   языке вопроса (это обнаружено при измерении на реальной базе). Оценка единицы поиска — косинус
   TF-IDF, умноженный на покрытие запроса (долю его слов, найденных в тексте): без этого короткая
   запись из одного названия обгоняла статью, где найдены все слова запроса, но которая длиннее. Если настроен сервис
   эмбеддингов, добавляется поиск по смыслу.
3. **Живой поиск в OpenAlex и Crossref** (аннотации найденных статей; язык выбирается под чатом).

После генерации ответ **проверяется** (`app/services/citations.py`): номера `[n]`, которых нет
среди переданных источников, заменяются на `[?]`, а строки списка литературы, которые не
удаётся сопоставить с найденными источниками, помечаются предупреждением. Номера в ответе
кликабельны.

Ограничения:
- Без ключа LLM чат показывает найденное списком без пересказа.
- Ответ строится по аннотациям, а для открытых статей — и по полному тексту (см. ниже). Если ни того
  ни другого нет, модель может только упомянуть, что публикация существует.
- Если OpenAlex/Crossref не ответили (лимит, нет сети), чат об этом сообщает и отвечает по локальной базе.
- Один вопрос = до двух коротких вызовов LLM для формулировок запроса, один вызов для ответа,
  по запросу в OpenAlex и Crossref. Внешний поиск отключается галочкой под чатом.

### Полные тексты открытых статей

Вкладка «Наполнение базы» → «Полные тексты открытых статей» (`POST /api/fulltext/fetch`). Для
публикаций с DOI система узнаёт у OpenAlex ссылку на открытый PDF, скачивает его (лимит 20 МБ,
60 страниц), извлекает текст (pypdf, чистый Python) и добавляет в поиск. Закрытые статьи не
загружаются; сканы без текстового слоя пропускаются (OCR нет). Сбой одной статьи не влияет на
остальные.

### Онтология и логический вывод

**Онтология первична.** Структуру (классы, свойства, подклассы, транзитивность, обратные свойства, области определения)
задаёт ваш файл онтологии `data/oil-gas-ontology.owl` (Protégé); он создан раньше базы данных. БД поставляет только
экземпляры и связывается с онтологией по явной таблице соответствия (страница «Онтология», `GET /api/ontology/mapping`).
Экземпляры из самого файла (демонстрационные Иванов 2005 и т. д.) в онтологию приложения не переносятся: вместо них
экземпляры берутся из БД. Файл можно править в Protégé и сохранять (Turtle или RDF/XML): приложение подхватит изменения
само, без перезапуска. Другой файл задаётся переменной `ONTOLOGY_FILE`; если файла нет, используется встроенная копия
структуры.

Соответствие БД ↔ онтология (полная таблица с пометками на странице «Онтология»):

| Онтология | БД |
|---|---|
| классы Провинция, Область, Район, Месторождение, Пласт, Залежь | таблицы province, oblast, rayon, field, horizon, deposit |
| класс Публикация и свойства название, год, журнал, ссылка | таблица publication и её столбцы |
| входитВ (транзитивно), имеетМесторождение / имеетПласт / имеетЗалежь | внешние ключи иерархии (ребёнок → родитель и обратно) |
| относитсяКОбъекту | publication_field, publication_horizon, publication_deposit |
| относитсяКТипуИсследования, класс Исследование и его подклассы | publication_research_type и research_type: тип «Геологическое» → экземпляр `Геологическое_исследование` класса Геологическое |
| автор | author и publication_author (ФИО, по одному значению на автора) |
| ЗонаНефтегазонакопления | таблицы нет, экземпляров пока нет (так и сказано в таблице) |
| записьБД (расширение) | ключ строки БД у каждого экземпляра, например `rayon:1` |

**Расширения приложения** (в вашем файле их нет; в онтологии каждое помечено комментарием «Расширение приложения»):
цепочка свойств `относитсяКОбъекту ∘ входитВ ⊑ относитсяКОбъекту`; обратное свойство `имеетПубликацию`; непересекающиеся
классы (ошибки данных находятся как противоречия); определяемые классы «Публикация района/области/провинции X» и
«Публикация типа T» (автоклассификация); свойства-данные DOI, описание, годОткрытия, координаты, записьБД; классы для типов
исследований из БД, которых нет в онтологии (если появятся). Всё остальное взято из вашего файла без изменений.

Что выводится из записанных в базе фактов:

| Аксиома | Что выводится |
|---|---|
| `входитВ` транзитивно (ваш файл) | залежь → пласт → месторождение → район → область → провинция целиком, хотя в базе записаны только соседние уровни |
| `содержит` — обратное к `входитВ` (ваш файл) | обратные связи |
| цепочка свойств (расширение) | публикация про пласт относится и к месторождению, району, области, провинции |
| подклассы НефтегазовыйОбъект и Исследование (ваш файл) | любой пласт, район и т. д. — нефтегазовый объект; «Геологическое_исследование» — исследование |
| определяемые классы (расширение) | публикации классифицируются автоматически |
| непересекающиеся классы (расширение) | объект одновременно район и месторождение — противоречие |

Рассуждатель приложения — OWL 2 RL (библиотека owlrl, чистый Python, без компилируемых частей). Все аксиомы лежат в этом
профиле. **Результат сверяется со стандартным HermiT** на вашей онтологии: `python -m scripts.ontology_check --hermit`
(нужны `pip install owlready2` и Java) сравнивает связи «входит в», связи публикаций с объектами и членство в определяемых
классах. На тестовой базе из 155 публикаций совпало 88 из 88, 155 из 155 и 1705 из 1705. Файл можно скачать на странице
(или `GET /api/ontology/export`) и открыть в Protégé: HermiT даст тот же результат. Кроме того, вывод проверяется на
совпадение с рекурсивными SQL-запросами для каждого объекта (`GET /api/ontology/validate`).

SPARQL на странице: можно писать как `:Район`, так и `ontology:Район` (как в запросах лабораторной работы); префиксы
подставляются сами (приложение приводит запрос к одному префиксу: библиотека rdflib не держит два префикса на один адрес).
Разрешены только SELECT и ASK.

В чате, если в вопросе назван район, месторождение, пласт и т. п., под ответом показывается результат по онтологии: сколько
публикаций записано напрямую и сколько найдено выводом, с цепочкой рассуждения; это же число попадает в справку для языковой
модели.

Ограничения:
- рассуждатель приложения — OWL 2 RL, а не полный OWL DL. Например, HermiT сам обнаруживает, что класс «Публикации района X»
  входит в класс «Публикации области Y» (иерархию классов), а приложение вычисляет членство публикаций, которое от этого не
  зависит (оно совпадает); для работы с иерархией классов используйте Protégé;
- построение занимает секунды: около 3 с на 150 публикациях и около 16 с на 1000; результат кэшируется, после изменения данных
  пересчёт идёт в фоне (чат его не ждёт, страница «Онтология» ждёт);
- правки сделанные в приложении или БД в онтологию-файл не возвращаются: файл — источник структуры, БД — источник экземпляров;
- класс ЗонаНефтегазонакопления и тип «Геокриологическое» в вашей онтологии есть, но в БД для них нет данных;
- вопросы на естественном языке не переводятся в SPARQL языковой моделью (как в лабораторной на Gradio): SPARQL пишется
  вручную на странице, а чат использует онтологию для поиска и объяснения по названному в вопросе объекту.

### Смысловой поиск через эмбеддинги (необязательно)

Нужен для случаев, когда вопрос и текст выражают одно и то же разными словами. Работает через
любой сервис с OpenAI-совместимым методом `/embeddings` (настройка в `.env`, см. `.env.example`),
локальная модель не требуется. Векторы хранятся в таблице `publication_embedding` (служебная,
создаётся сама), считаются после каждого сохранения публикаций и командой
`python -m scripts.build_embeddings`. Без ключа функция выключена, и система работает как раньше.
Порог схожести `EMBEDDINGS_MIN_SIM` подбирается на вашей базе: `python -m scripts.eval_chat calibrate`.
Пример настройки для Gemini приведён в `.env.example`; Google описывает свой слой совместимости
с OpenAI как бета-версию, а бесплатный тариф ограничивает число запросов в минуту (при лимитах
запросы повторяются с задержкой).

### Измерение качества

Без цифр нельзя сказать, что система стала лучше. `python -m scripts.eval_chat` измеряет качество
на ВАШЕЙ базе и сохраняет отчёт в `eval/` (его можно вставить в диссертацию, раздел 3.8.3):

```
python -m scripts.eval_chat retrieval              # поиск: прежний и новый, Hit@5, Precision@5, MRR
python -m scripts.eval_chat generate --n 25        # LLM придумывает вопросы по аннотациям
python -m scripts.eval_chat retrieval --llm-rewrite
python -m scripts.eval_chat retrieval --details    # диагностика: где и почему новый поиск хуже прежнего
python -m scripts.eval_chat answers --n 10         # ссылки в ответах, язык, время
python -m scripts.eval_chat calibrate              # порог для эмбеддингов
python -m scripts.eval_chat behavior               # разговор, «что ты умеешь», вне темы, без ответа в базе
python -m scripts.eval_chat scope --fast           # точность классификатора темы (36 вопросов), пороги для эмбеддингов
python -m scripts.eval_chat scope                  # то же, но через полный /api/chat (без внешнего поиска)
python -m scripts.eval_chat scope --api http://127.0.0.1:8001   # через запущенный сервер
```

Режим `--details` добавляет в отчёт таблицу по каждому вопросу, состав «лишних» результатов в первой
пятёрке (язык, наличие аннотации, какой вариант запроса и какая единица дали оценку) и разбор
проблемных вопросов. По нему видно причину, а не только цифру. Для 24 вопросов один вопрос меняет
среднюю примерно на 0,04, поэтому разницу в 1–2 вопроса не стоит считать закономерностью.

Режим `behavior` (`eval/behavior.json`) проверяет четыре вида вопросов: разговорные (ответ мгновенный, без
источников), «что ты умеешь», вне темы (вежливое объяснение, публикации не ищутся) и **по теме, но без ответа в базе**.
Для последних проверяется честность: признаёт ли бот отсутствие информации и нет ли в ответе чисел, которых нет
ни в источниках, ни в вопросе. Это эвристика выдумки: она не доказывает правдивость, но выдуманные цифры
(«в 2023 году добыто 18 млн т») ловит хорошо. Подозрительные ответы просматривайте глазами.

Банк вопросов `eval/questions.json` (24 вопроса; русские и английские формулировки; релевантность
задаётся регулярным выражением по названию и аннотации) можно править под свою тему. Вопросы, на
которые в базе нет ни одной подходящей публикации, в расчёт не берутся.

### Тесты

### Наполнение базы реальными публикациями

Вкладка **«Наполнение базы»** (или `POST /api/import/preview` и `POST /api/import/commit`):

1. «Найти кандидатов» — по набору запросов (стандартный набор можно менять) система ищет в
   OpenAlex и Crossref и **ничего не сохраняет**.
2. Из найденного отбрасывается всё, что не про предметную область (нужно и упоминание региона,
   и нефтегазово-геологическая тематика — поэтому статьи про политику Польши или историю
   Урала отсеиваются), и всё, что уже есть в базе (по DOI или названию).
3. Для оставшихся предлагается привязка к месторождению (по упоминанию «Шаим», «Шушма»,
   «Ловин» и т. п.) и тип исследования (по ключевым словам). Это правила, а не понимание
   текста, поэтому список нужно просмотреть: у сомнительных снимите галочку.
4. «Сохранить выбранные» записывает отмеченное. Аннотация сохраняется как фрагмент текста в служебной
   таблице `document_chunk` (в схеме `publication` из лабораторной работы колонки под неё нет, а схему
   менять нельзя), поэтому она участвует в локальном поиске и попадает в контекст LLM. Авторы нормализуются (один человек — одна запись),
   поля обрезаются до размеров колонок, сбой на одной публикации не отменяет остальные.

В чате у каждого внешнего источника есть кнопка «в базу» (привязка определяется автоматически).

**Важно перед первым запуском:** получите бесплатный ключ OpenAlex
(https://openalex.org/settings/api) и добавьте в `.env` строку `OPENALEX_API_KEY=...`.
Без ключа дневной лимит поиска в OpenAlex по документации очень мал, а стандартный набор —
16 запросов.

  исследований** взяты из документов вашей работы.
- **Параметры месторождений** заполнены только там, где их удалось подтвердить:
  Шаимское (Трёхозёрное): открыто 21 июня 1960 г., разработка с 1964 г. (ЦДУ ТЭК, cdu.ru, 2020);
  Шушминское: открыто в 1985 г., координаты 61,1667; 64,1333 (каталог НефтьГазИнформ, oilgasinform.ru);
  Ловинское: открыто в 1973 г., координаты 61,25; 65,00 (nftn.ru).
  **Не заполнено намеренно:** координаты Шаимского, глубина, обводнённость, параметры пласта,
  запасы. В первой версии тестовых данных в этих полях стояли числа, которых нет ни в одном
  источнике; их нужно заменить (см. ниже). Пустые поля интерфейс не показывает, а чат-бот не
  домысливает.
- **Пять демонстрационных публикаций** (Иванов 2005, Сидоров 2010 и др.) вымышленные, их ссылки
  ведут на несуществующий example.ru. Для реальной базы их нужно удалить.

Если у вас уже есть база со старыми значениями, не запускайте `seed_db` (он стирает всё), а
выполните безопасный перенос:

```
python -m scripts.clean_demo_data                                  # показать план, ничего не меняя
python -m scripts.clean_demo_data --apply                          # заменить только выдуманные значения
python -m scripts.clean_demo_data --apply --delete-demo-publications
```

Скрипт меняет только то, что всё ещё равно прежним выдуманным значениям: ваши правки не затрагиваются.

Чтобы добавить координаты Шаимского месторождения (они нужны, чтобы оно появилось на карте),
найдите проверенное значение (например, в каталоге НефтьГазИнформ или Wikidata) и выполните:

## Известные ограничения / точки расширения

- **Координаты есть только у `field`.** Province/oblast/rayon/horizon/deposit
  не имеют пространственной привязки в исходной модели — карта
  показывает только месторождения. Если нужны полигоны границ района
  или области — это расширение модели сверх лабораторной работы.
- **Разбор ФИО из внешних источников — эвристика.** OpenAlex/Crossref
  отдают имя одной строкой ("Ivan Petrov"), а схема требует отдельные
  `last_name`/`first_name`/`middle_name`. Разбор (`_parse_author_name`
  в `app/main.py`) берёт последнее слово как фамилию — работает для
  большинства западных имён, но не идеален для всех случаев.
- **pgvector** упомянут в разделе 2 лабораторной работы как причина
  выбора PostgreSQL, но ни одна таблица в разделе 3 не содержит колонку
  эмбеддинга — поэтому `CREATE EXTENSION vector` в `schema_lab9.sql`
  закомментирован по умолчанию (не требует обязательной установки).


## Тема вопроса, кэш и журнал запросов (v29)

- **Классификатор темы** (`app/scope_embed.py`, `llm.classify_scope`): порядок «кэш → эмбеддинги → ключевые слова → LLM».
  Эмбеддинги сравнивают вопрос с центроидом эталонных фраз (названия районов, месторождений, пластов, типы
  исследований из базы + статический набор). Два порога `SCOPE_SIM_LOW` / `SCOPE_SIM_HIGH`; между ними решают
  ключевые слова и LLM. Без `EMBEDDINGS_API_KEY` или при сбое сервиса (пауза 60 с) работают ключевые слова.
  Слова-«ложные друзья» («пластик», «газета») вырезаются до поиска (`services/text_utils.py`).
- **Кэш** (`app/telemetry.py`): LRU в памяти для классификации и переписанных запросов, `LLM_CACHE_SIZE` (1000; 0 — выкл.).
  Сбои (`None`) не кэшируются.
- **Повтор при сбое**: один автоматический повтор вызова LLM при сетевой ошибке/таймауте/лимите; ошибки ключа и
  некорректного запроса (400/401/403/404/422) не повторяются.
- **Журнал**: `logs/chat_logs.jsonl`, одна строка JSON на запрос: `timestamp, query, scope, scope_method,
  rewritten_query, sources_found, provider, latency_ms, tokens_used, llm_calls, retries, cache_hits`.
  Это тексты вопросов пользователей: храните файл локально, `CHAT_LOG=0` отключает запись.

## v32: привязка публикаций к району, области и провинции

Раньше публикацию можно было привязать только к месторождению, пласту или залежи. Большинство найденных работ
посвящено региону в целом, поэтому оставалось без привязки. Теперь хранится **самый конкретный уровень**
(месторождение → район → область → провинция), определённый по тексту; вышестоящие уровни выводятся по иерархии
(работа о месторождении относится и к его району; работа о провинции не «опускается» на конкретное месторождение).

- Новые таблицы `publication_rayon`, `publication_oblast`, `publication_province` создаются при запуске сами
  (см. также `db/schema_regions_ext.sql`); существующие данные не затрагиваются.
- «Shaim oil and gas region» привязывается к **району**, «Shaim oil field» — к **месторождению** (раньше обе — к месторождению).
- Онтология: те же связи `относитсяКОбъекту` для района, области и провинции; проверка `/api/ontology/validate` учитывает их.
- `/api/stats` → `publications_by_level`; отчёт `bulk_import` содержит раздел «Уровень привязки к иерархии».

Для уже загруженных публикаций:
```
python -m scripts.assign_regions                  # пробный прогон
python -m scripts.assign_regions --apply          # добавить привязки к району/области/провинции
python -m scripts.assign_regions --apply --tighten   # + заменить «районную» привязку к месторождению на привязку к району
```

## v34 — маршрутизация по намерениям (Intent-Aware Routing)

Перед поиском LLM одним словом определяет тип вопроса (`llm.detect_intent`, ~10 токенов, без контекста публикаций,
кэшируется по тексту; без LLM — `FIND_PUBLICATION`). Вызов идёт параллельно с переписыванием запроса — задержки не добавляет.

| Намерение | Поиск | Инструкция ответа |
|---|---|---|
| `FIND_PUBLICATION` | обычный гибридный | обзор статей, группировка по годам/методам, авторы |
| `FIND_OBJECT` | объект из базы → его публикации → родители по онтологии (пласт → месторождение → район → область → провинция) → обычный поиск | геологическая справка + список публикаций |
| `COMPARE_OBJECTS` | вопрос делится на два объекта (правила, затем LLM), два поиска, чередующееся объединение | таблица/список «Сходства / Различия» только по источникам |
| `EXPLAIN` | обычный | короткое определение |
| `OFFTOPIC` | нет (короткий отказ). Игнорируется, если тема уже подтверждена словами предметной области или это уточнение | — |
| `UNKNOWN` | как `FIND_PUBLICATION` | — |

В `logs/chat_logs.jsonl` добавлены `query_intent` и `route` (`standard`, `object`, `compare`, `standard:compare-not-split`, `offtopic:scope|intent`);
в ответе `/api/chat` — `query_intent` и `search_strategy`. Прежнее поле `intent` (тема: smalltalk/domain/…) не менялось.

Точность: `python -m scripts.eval_chat intent` (нужен ключ LLM) — 24 вопроса из `eval/intent_questions.json`, Accuracy, precision/recall по классам, матрица ошибок.

## v35 — вход, роли, экспорт, фильтр внешней выдачи

**Авторизация** (`app/auth.py`, только стандартная библиотека — новых пакетов нет). Таблица `app_user` создаётся сама при запуске.
- `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`. Первый зарегистрированный пользователь — администратор (или email из `ADMIN_EMAIL`).
- Читать и искать (карта, поиск, чат) можно без входа. Нужен вход: загрузка документа, сохранение из внешнего поиска, загрузка полных текстов, экспорт. Только администратор: удаление публикаций, импорт, построение эмбеддингов.
- Пароль — PBKDF2-SHA256 с солью; токен — JWT HS256 (срок `AUTH_TOKEN_HOURS`, по умолчанию 12 ч). Ключ: `AUTH_SECRET` в `.env` или файл `.auth_secret`, который создаётся сам (в git не попадает).
- `AUTH_ENFORCE=0` в `.env` отключает защиту (разработка); кнопка «Войти» тогда скрыта.

**Экспорт** `POST /api/export` `{publication_ids, format}`: `csv` (Excel, UTF-8 с BOM, `;`), `bibtex`, `ris`, `json`; порядок как в выдаче, до 500 записей. Ячейки CSV, начинающиеся с `= + - @`, обезврежены. Кнопка «Экспорт» есть под результатами поиска, под источниками в чате и на странице «Публикации».

**Фильтр внешней выдачи в чате**: из OpenAlex/Crossref остаются работы, где есть признак Западной Сибири и нефтегазовой геологии (те же правила, что при импорте). Отключается `EXTERNAL_DOMAIN_FILTER=0`.

**Демо-записи** (example.ru и подставные значения месторождений): `python -m scripts.clean_demo_data` (план), затем `--apply --delete-demo-publications`.

## v36 — сравнение объектов таблицей

## v37 — чат с историей (как в DeepSeek)

**Интерфейс** (`ChatPage.jsx`, `ChatSidebar.jsx`): слева панель 260 px (кнопка «Новый чат», список чатов с названием — первые 30 символов первого вопроса — и временем, внизу профиль или «Войти»), справа светлый чат. На экране уже 768 px панель скрыта и открывается кнопкой ☰. Корзина на пункте списка удаляет чат (только свои), при пустом списке показывается «У вас пока нет сохраненных чатов».

**Гость**: чат работает без входа, один текущий чат, после перезагрузки страницы он пропадает. «Новый чат» у гостя открывает окно «Войдите, чтобы сохранять историю…». Выбор языка внешнего поиска доступен гостю.

**Вошедший пользователь**: чат создаётся при первом вопросе (пустые чаты в базе не копятся); `POST /api/chat` и `/api/chat/stream` принимают `session_id`; вопрос и ответ записываются в БД **только после того, как ответ готов целиком** — при ошибке или нажатии «Стоп» в историю ничего не попадает. Вместе с ответом хранится JSON (источники, ссылки, оценка надёжности), поэтому старый чат открывается как был.

**API**: `GET/POST /api/chat/sessions`, `GET /api/chat/sessions/{id}/messages`, `DELETE /api/chat/sessions/{id}`. Чужой чат отвечает 404, гость — 401. Таблицы `chat_sessions` и `chat_messages` создаются автоматически при запуске.

## v38 — роли и админ-панель

**Доступ по ролям** (`frontend/src/roles.js`, хук `useRole`; настоящая защита — на сервере):

| Роль | Вкладки |
|---|---|
| гость | Главная, Поиск и карта, ИИ-Ассистент (один чат без сохранения) |
| `user` | + Публикации, Внешний поиск, история чатов, экспорт |
| `admin` | + Наполнение базы, Онтология, Админ-панель |

Закрытая вкладка гостю предлагает войти, остальным не открывается; при выходе или блокировке пользователь с закрытой страницы возвращается на «Главную». Кнопки «в базу» (сохранение из внешнего поиска) видны только администратору.

**Сервер**: любое изменение данных — только `admin` (импорт, удаление и ручное добавление публикаций, сохранение из внешнего поиска, загрузка документов и полных текстов, эмбеддинги). Без токена — 401 (чтобы интерфейс предложил войти), с токеном обычного пользователя — 403.

**Админ-панель** (`/api/admin/*`, вкладка «Админ-панель»):
- **Пользователи** — ID, email, роль (можно менять), дата регистрации, число чатов, «Заблокировать / Разблокировать». Нельзя заблокировать или разжаловать себя и последнего администратора; токен заблокированного перестаёт действовать сразу.
- **Публикации** — поиск, «Добавить вручную», «Редактировать», «Удалить» (дубликат по DOI/названию не создаётся). Привязку новых записей к объектам делает `python -m scripts.assign_regions --apply`.
- **Логи** — последние записи `logs/chat_logs.jsonl`: время, кто (email или «гость»), вопрос, намерение, маршрут, число источников, время ответа, токены.
- **Настройки** — включение/выключение OpenAlex и Crossref и смена модели LLM без перезапуска (таблица `app_setting`).
